# Sentry Setup (Error Monitoring)

Sentry captures unhandled exceptions and explicitly-reported errors/warnings from both the server and the browser. It is **optional** — the app runs identically with it disabled, which is the default.

**Data source:** [sentry.io](https://sentry.io) — commercial SaaS, generous free tier.

---

## 1. Create a project

1. Go to [sentry.io](https://sentry.io) and sign in (or create a free account).
2. Create a new project → select **Next.js** as the platform.
3. Note the **DSN** shown during setup (also available later under **Settings → Projects → [project] → Client Keys (DSN)**). The DSN is safe to expose publicly — it identifies where events go, not who can read them.

---

## 2. Add to environment

```bash
NEXT_PUBLIC_SENTRY_DSN=<your-dsn>
NEXT_PUBLIC_ENABLE_SENTRY=true
```

Both are required — the DSN alone does not activate reporting. `NEXT_PUBLIC_ENABLE_SENTRY` is a separate kill switch (`src/lib/monitoring/config.ts`) so Sentry can be disabled instantly without touching the DSN, and so local development never reports by default even if a DSN happens to be present in `.env.local`.

For source-map upload at build time, also set in Vercel (not needed locally):

```bash
SENTRY_ORG=mketiku
SENTRY_PROJECT=nycgrid
SENTRY_AUTH_TOKEN=<from Settings → Auth Tokens, scope: project:releases>
```

These three are already listed in [`vercel.md`](./vercel.md)'s environment variable table.

---

## 3. How it works

- **Single choke point**: all app code reports through `captureAppError()` / `captureAppWarning()` in `src/lib/monitoring/sentry.ts` — never `Sentry.captureException` directly. This is enforced by the `local/no-direct-sentry-capture` ESLint rule. `normalizeError()` coerces non-`Error` values (DOM Events, `{message, code}`-shaped objects, strings, `undefined`) into titled Errors so Sentry can group them — raw values otherwise produce untitled, ungroupable "Object/Event captured as exception" noise.
- **Environment resolution**: `NEXT_PUBLIC_APP_ENV` → `VERCEL_ENV` → `NODE_ENV`, so events are tagged `development`/`preview`/`production` without a separate `SENTRY_ENV` variable.
- **Same-origin tunnel**: client events post to `/api/sentry-tunnel` (auto-generated by the Sentry webpack plugin via `tunnelRoute` in `next.config.ts`) instead of directly to `sentry.io`, so ad blockers don't intercept them. No CSP change was needed for this — it's same-origin.
- **Release tracking**: every event is tagged with `${package.json version}+${git short SHA}`, so a spike can be traced to the deploy that caused it. Releases are only created for production deploys (`VERCEL_ENV === "production"`) — preview releases would be throwaway noise.
- **Source maps**: uploaded at build time, then deleted from the deployed output (`deleteSourcemapsAfterUpload: true`) so original source isn't publicly fetchable. Upload is skipped entirely when `NEXT_PUBLIC_ENABLE_SENTRY` isn't `"true"`.

---

## 4. What's NOT wired up (and why)

- **Session Replay** — not enabled. nycgrid has no consent/privacy-notice flow, and the app surfaces camera imagery and user-generated photobooth captures; recording sessions without an explicit privacy review is a separate decision, not a side effect of adding error monitoring.
- **User identity / `setSentryUser`** — not applicable. nycgrid has no accounts or auth.
- **PostHog↔Sentry correlation** — not wired. Would require its own review of what session data crosses between the two tools.

---

## 5. Privacy impact

No PII is captured. There's no auth, no session replay, and no user-identifying data in any `captureAppError`/`captureAppWarning` call site — only route/feature tags and short error messages from upstream API failures (ArcGIS, NYC DOT, Ticketmaster/511/BusTime). Browser events include standard client metadata (URL, user agent, stack trace) but nothing entered by the user.

---

## 6. Free-tier budget

Sentry's free tier is 5,000 error events/month. nycgrid's actual traffic is very low (roughly a few hundred visitors/month) and nearly all wired capture points are for _expected, recoverable_ upstream failures (`captureAppWarning`, not exceptions) with `tracesSampleRate: 0.1` — performance tracing samples 1 in 10 requests, not every request. There's effectively no realistic path to exceeding the free tier at current traffic; revisit sampling if that changes.

---

## 7. Failure modes

- **SDK init failure** (bad DSN, network unreachable) is silent and never blocks the app — `Sentry.init` only runs inside an `if (enableSentry && dsn)` guard, and nothing downstream awaits it synchronously.
- **Sentry itself down**: `captureAppError`/`captureAppWarning` fire-and-forget; a failed send doesn't throw or delay the response to the user.
- **Disabled by default**: unless both `NEXT_PUBLIC_ENABLE_SENTRY=true` and a DSN are set, no code path calls into the Sentry SDK at all beyond the no-op config check — safe default for local dev and any environment where Sentry isn't configured.
